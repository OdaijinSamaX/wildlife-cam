# ハーネスの使い方と、各チェックの意味・閾値の根拠・限界

```bash
uv run python -m harness check designs/wildlife_cam/pir_bezel.py
```

で `out/pir_bezel/` に次が出る。

```
pir_bezel.step / .stl / .3mf     STEP は設計座標、STL と 3MF は造形姿勢を適用済み
views/front|back|left|right|top|bottom|iso.png
views/section_*.png              断面（既定は XZ 中央 / YZ 中央）
report.md                        画像 + 実測値 + PASS/FAIL
```

総合判定は `FAIL` があれば FAIL、`WARN` があれば WARN、それ以外は PASS。
終了コードは FAIL のときだけ 1。

## 判定の意味

| 表示 | 意味 |
|---|---|
| PASS | 閾値を満たした |
| FAIL | 閾値を満たさない。**人が見るまで先に進まない** |
| WARN | 判定を出せないか、人の確認が要る（例: 開口の宣言が無い） |
| SKIP | 対象が無い（例: COMPONENTS が空のときの clearance） |
| ERROR | チェック自体が例外で止まった。ハーネスのバグ |

## 内部で作っている表現

チェックはこのどれかの上で動く。`harness/geom.py` が唯一の変換口。

| 表現 | 作り方 | 使うチェック |
|---|---|---|
| B-rep (OCC) | `build()` の戻り値そのもの | manifold, bbox, interference, clearance, openings |
| 三角メッシュ | `Shape.tessellate(0.05, 0.2)` + 頂点マージ | manifold, wall, overhang, render |
| ボクセル | z ごとに断面ポリゴンを取り shapely で内外判定 | openings |
| 宣言 (claim) | 設計側の `features(p)` | layout |
| 補正テーブル | 設計側の `FIT_TABLE` | fit |

テッセレーション公差 0.05 mm は「0.4 mm ノズルの造形誤差より十分細かく、かつ
三角形数が爆発しない」ところ。**これより細かい形状の破綻はメッシュ側では見えない。**

ボクセル化は表面ボクセル + 穴埋めではなく断面ラスタライズでやっている。
穴埋め方式だと「閉じた空洞」と「材料」が区別できず、openings が成立しないため。

## 0. fit — 寸法補正テーブルの素性と適用記録

**見るもの**: 設計が宣言した `FIT_TABLE` が何で、どの寸法にいくら足されたか。

設計スクリプトは **狙い寸法**（印刷後にこうなってほしい寸法）を書き、補正は
`harness/fit.py` のテーブルが一箇所で当てる。そのテーブルは
**材料・機種・ノズル径・造形姿勢** の組にしか意味がないので、素性
（材料 / 機種 / ノズル / 層厚 / 姿勢 / 実測日 / 実測値の出所）を毎回表示する。

**ハーネスは `build()` を 2 回評価する。**

| モード | 例: `hole(10.1)` | 使い道 |
|---|---|---|
| `target` | 10.1 | **全てのチェックとレンダ** |
| `print` | 10.4 | **STL / 3MF の書き出し** |

こうしないと `clearance` や `wall` が「補正で膨らんだ穴」を測ってしまい、
実物と違う数字で PASS/FAIL を出すことになる。STEP は狙い形状、
STL と 3MF は補正済み形状で、その体積差も measurements に出る。

**判定**:

| 状態 | 判定 |
|---|---|
| `FIT_TABLE` が未宣言 | **FAIL** |
| `fit.NONE`（意図した無補正）を宣言 | PASS |
| テーブルを宣言したが一度も通していない | WARN |
| 暫定値 / 外挿 / 無補正 を含む | WARN |
| それ以外 | PASS |

現行テーブル `asa-p1s-0.4mm-2026-08-22`（ASA / P1S / 0.4 mm / 0.2 mm / 平置き）:

| 種類 | 範囲 | delta | 実測点 |
|---|---|---|---|
| `wall` | 全域 | +0.00 | 4 |
| `hole` | φ8.0 以上 | +0.30 | 4 |
| `hole` | φ2.0 〜 5.0 | +0.25（暫定） | 6 |
| `boss` | 全域 | +0.25 | 1 |

生の実測値と導出の計算は `designs/wildlife_cam/fit_coupon.md`。

**限界**:
- 設計が `FIT_TABLE` を呼ばずに書いた寸法は表に出ない。**通した寸法の記録**で
  あって、網羅を強制する仕組みではない
- テーブルの素性と実際の印刷条件が一致しているかは人が確認する
- 溝幅・角穴・ポケットなど、まだ実測していない種類には規則が無い

## 1. manifold — 水密・多様体か

**見るもの**: B-rep 側は `BRepCheck_Analyzer`、メッシュ側は境界エッジ数・
非多様体エッジ数・巻き方向の一貫性・体積の一致。

**判定**: B-rep が不正、または境界エッジ / 非多様体エッジがあれば FAIL。
メッシュ体積が B-rep 体積と 2% 以上ずれたら WARN（テッセレーションが粗すぎる）。

**なぜ両方見るか**: 片方だけだと「B-rep は正しいがテッセレーションが破綻」と
「メッシュは閉じているが B-rep が自己交差」のどちらかを取り逃がす。
実際、pir_bezel の回転軸を間違えて体積 0 の板になったとき、これが最初に鳴った。

**限界**: テッセレーション公差より細かい破綻。複数ソリッドが面で接しているだけの
状態（体積 0 なので interference も PASS になる）。

## 2. wall — 最小肉厚

**手法**: 表面を面積重み付きで 6000 点サンプリングし、各点から内向き法線方向に
レイを飛ばして最初に当たる裏面までの距離を測る（レイキャスト法）。

凹角では隣の壁に当たって偽の薄肉が出るので、**当たった面の法線がレイと 25 度以内で
平行なものだけ**を採用する。向かい合う壁だけを測るという意味。

**判定に使う値**: `robust_min_wall_mm` = 「min_samples（既定 5）本以上のレイが
下回る厚み」。単発の最小値 `min_wall_mm` も併記するが判定には使わない。

なぜ分けるか: 刻印文字の鋭角部やフィレットの端では 1 本だけ 0.3 mm のような値が
出る。それは構造としての薄肉ではない。実際 fit_coupon では、文字サイズ 4.0 mm の
刻印が 0.28 mm の単発値を出したので、文字を 6.0 mm に上げた。
**単発値も報告するのは、そういう「印刷できない微細形状」に気づくため。**

**閾値の根拠**: 既定 1.6 mm = 0.4 mm 押出幅 x 4（外壁 2 + 内壁 2）。屋外品で
割れない下限。0.01 mm の測定ノイズ許容（`wall_tolerance_mm`）を引いて比較する。

**限界**:
- サンプル点が乗らないほど小さい薄肉パッチは見逃す（既定 6000 点）
- 向かい合う面の角度差が 25 度を超える楔形の薄肉は測れない
- レイは法線方向にしか飛ばさないので、斜め方向が最短になる形状は過大評価する
- 「薄いこと」しか見ない。長い薄板が曲がるかどうかは判定していない
  -> **パッキンを潰す合わせ面については `seal` チェック（10）が別に見る**

## 3. bbox — 造形サイズ枠

**手法**: `PRINT_ORIENTATION` を適用してビルドプレートに落としてから外接直方体を測る。

**閾値の根拠**: 256 x 256 x 256 mm = Bambu Lab P1S のビルドボリューム。

**限界**: 枠に入っても実際には置けないケース（プレート端のクリップ、パージタワー、
複数部品の同時配置）は見ていない。姿勢は `PRINT_ORIENTATION` の 1 通りしか試さない
ので、寝かせれば入る形状を FAIL にすることがある。

---

## 4. interference — ソリッド同士の干渉

**手法**: `build()` が返した形状の中のソリッドを総当たりでブーリアン積し、体積が
`interference_volume_tol_mm3`（既定 1e-3）を超えたら FAIL。

**限界**: 面が完全に一致して接触しているだけの状態は体積 0 なので PASS になる。
ソリッド数の 2 乗でブーリアンを回すので数十個を超えると重い。

---

## 5. layout — 単一ソリッド内のフィーチャの食い合い

**なぜ要るのか**: `interference` は別ソリッド同士しか見ない。`openings` は溝を
止まり穴としか見ない。そのため「1 個のソリッドの中でフィーチャが場所を奪い合って
いる」状態を拾う手段が無かった。

実際に出た不具合: fit_coupon 初版で、O リング溝の帯（中心 30,-17 / r 13.65..16.35）が
基準ピン φ10.0（中心 26,3 / r 5）の根元を **0.95 mm 削っていた**。
中心間距離 20.40 mm に対し、必要なのは 16.35 + 5.00 = 21.35 mm。
`overhang` が z=8 に span 0.95 mm の下向き面として症状だけ報告していたが、
「なぜ空中に床があるのか」は誰も読めなかった。

**手法**: 設計側が `features(p)` で各フィーチャの占有領域（claim）を宣言し、

1. claim を総当たりでブーリアン積し、体積が 0 でなければ FAIL
   （バウンディングボックスが重ならない組は事前に落とす。fit_coupon では
   528 組のうち実際にブーリアンを回すのは 1 組だけ）
2. B-rep から見つかった穴（内向き円筒面）が、どの claim にも入っていなければ FAIL
   — 宣言し忘れたフィーチャは衝突判定の対象外になってしまうため

**claim の規約（ここを外すと検出できない）**:

**claim は「フィーチャ自身の体積」ではなく「そのフィーチャが所有すべき材料領域」。**

| フィーチャ | claim の z 範囲 |
|---|---|
| 台座から立つボス・ピン・フィン | **足元の板を厚み方向いっぱいまで** |
| 止まり穴 | 空洞 + その下に残すべき肉 (min_wall) |
| 貫通穴 | 板厚いっぱい |
| 溝 | 溝 + 反対側に残すべき肉 |
| 刻印 | 彫り込む深さぶん |

ピン (z=8..20) と溝 (z=6.5..8) は**体積が重ならない**。自分の体積だけを claim
すると、まさに今回の不具合をそのまま取り逃がす。ここが設計の肝。

マージンの既定は `min_wall / 2`。2 つの claim が重なった時点で、フィーチャ間に
残る材料が min_wall を下回っている、という意味になる。マージンは横方向にだけ効く
（z 方向は上の表のとおり設計側が明示する）。

溝は `feature.ring()` で環として宣言する。バウンディングボックスで包むと帯の
内側の広い land まで占有したことになり、そこに何も置けなくなる。

同軸に積み上がっていて**接するのが正しい**フィーチャ（座ぐり / 内径の溝 / 面取り）は
ひとつの claim にまとめる。pir_bezel の `bore_column` がその例。

**判定**: 宣言が無ければ WARN（黙って PASS にはしない）。重なりまたは宣言し忘れが
あれば FAIL。

**限界**:
- 宣言が実物とずれていればすり抜ける。`build()` と `features()` は必ず同じ
  PARAMS・同じ位置関数から組み立てること
- 穴以外（ボス・刻印・溝の内壁）は宣言し忘れても検出できない
- 部品の外形線からの距離（縁までの肉）は見ていない
- claim は Z 軸方向の円柱・円環・直方体と、任意形状のバウンディングボックスしか
  作れない。斜めの穴や複雑なポケットは過大に包むことになる

## 6. clearance — 内蔵部品との干渉

**手法**: 各 `Component` の `envelope(clearance)` と筐体ソリッドのブーリアン積。
実体（`shape`）との積も別に取り、「実体が当たっている」のか「クリアランスだけ
足りない」のかを区別して報告する。

envelope は部品側が寸法から作り直す。OCC のオフセット演算は形状によっては
体積が減るなど信用できなかったので使っていない。`Component` ではなく生の形状を
渡した場合だけバウンディングボックス近似になり、レポートに「bbox 近似」と出る。

**閾値の根拠**: 既定 0.4 mm は FDM の一般的な嵌合クリアランス。
封止のために意図的に詰める箇所（pir_bezel の内径 x ドーム）は設計側で
`component_clearance_mm` を下げ、理由を docstring に書く。

**限界**:
- 部品の envelope が実物より小さければすり抜ける（`parts/` の推定寸法に依存）
- 配線・コネクタの抜き差しスペース・組立時の斜め挿入は見ていない
- `COMPONENTS` に置かれていない部品は存在しないものとして扱う

## 7. overhang — 造形時の下向き面

**定義**: 面法線 n に対して `overhang_deg = degrees(asin(-n.z))`。
垂直な壁 = 0 度、水平な天井 = 90 度。

**手順**:
1. `PRINT_ORIENTATION` を適用してプレートに落とす
2. 閾値（既定 50 度）を超える面を拾う
3. 第 1 層（z <= zmin + 0.25 mm）に接する面は除外する（接地面は張り出しではない）
4. 残りを隣接関係で連結成分にまとめ、1 mm2 未満のパッチは捨てる
5. 各パッチの **渡り幅 = XY 投影の最大内接円の直径** を出す

**渡り幅に外接矩形の対角を使わない理由**: 幅 1 mm のリング状のひさし（O リング溝の
片側など）を「直径 30 mm の張り出し」と誤判定するから。最大内接円なら
リングの幅 1 mm がそのまま出る。shapely の負のバッファを二分探索して求めている。

**判定**: 残ったパッチが無ければ PASS。すべて渡り幅 10 mm 以下なら WARN
（ブリッジで渡せる）。10 mm を超えるパッチがあれば FAIL（サポートが要る）。

**閾値の根拠**: 50 度は ASA でサポート無しに刷れる限界のあたり。10 mm は
0.4 mm ノズルでブリッジが垂れずに渡る経験的な上限。

**限界**:
- 面の傾きしか見ていない。「下に支えがあるか」は判定していない
- 階段状に少しずつ張り出す形状（各面は閾値以下）は素通しする
- サポート材が実際に置けるか／剥がせるかはスライサでしか分からない

## 8. openings — 内外を貫通する開口

屋外筐体で「気づかないうちに水の入る穴が空いていた」を止めるための網。
**2 通りの見方を併用する。**

### A. B-rep パス（丸穴は厳密）

内向き円筒面（= 穴の内壁）を拾い、同軸・同径のものをまとめる。
各穴の軸方向の範囲を面の頂点から求め、その少し外側に探り点を置いて、
材料の中かどうかで **貫通 / 止まり** を分ける。

探り点は軸上ではなく **穴の内壁のすぐ内側（半径 r - 0.2 mm）** に置く。
軸上に置くと、貫通穴の中に掘った O リング溝まで「貫通」と判定されてしまう。

出るもの: 径、開口面積（pi r^2）、軸方向、中心座標、貫通/止まり。

### B. ボクセルパス（丸穴以外も拾う）

形状をボクセル化（既定ピッチ 0.5〜0.8 mm）して空気側の連結成分を取る。
外周に触れる成分が「外界」、触れない成分が「閉じた空洞」。

内部空間の代表点（`CHECK_CONFIG["interior_point"]`、省略時は最大の閉空洞の重心）が
外界とつながっていれば **漏れ経路あり**。さらにボール半径を 0.25 mm から 8 mm まで
増やしながらクロージングを掛け、内部が外界から切れた半径から
**最大の喉径（一番大きい隙間の直径）** を推定する。

丸穴でないスリットや分割線の隙間は、こちら側でしか見つからない。

### 判定

`CHECK_CONFIG["expected_openings"]` に開口を宣言してあれば、
検出した貫通穴と突き合わせて

- 宣言に無い貫通穴があれば FAIL（**意図しない穴**）
- 宣言した開口が見つからなければ FAIL（**穴の付け忘れ**）

宣言が無ければ WARN（表は出すので人が意図を確認する）。
`expect_sealed: True` を付けると、内部空間が外界に通じている時点で FAIL。

```python
CHECK_CONFIG = {
    "expected_openings": [
        {"diameter_mm": 23.4, "count": 1, "note": "PIR ドーム貫通口"},
        {"diameter_mm": 3.4,  "count": 4, "note": "M3 取付ねじ"},
    ],
    "openings_match_tol_mm": 0.1,   # 径の突き合わせ許容
}
```

**限界**:
- B-rep パスは円筒面しか見ない。角穴・スリット・分割線の隙間は表に出ない
  （ボクセルパスの漏れ判定でしか捕まらない）
- ボクセルパスはピッチ未満の隙間を「塞がっている」と見る
- 喉径のスイープは離散値（φ0.5〜φ16）で、その間は上側に丸める
- O リングやガスケットで「締めれば塞がる」隙間も開口として数える
- **開口が防水上安全かどうかは判定していない。** 位置と面積を出すだけで、
  そこにグランドやベントが付くのかは人が見る

## 10. seal — 締結点の間でパッキンの潰し量が保つか

**なぜ要るのか**: `wall` は「薄いこと」しか見ないので、**長い蓋が締結点の間で
たわんで辺の中央でパッキンが浮く**という失敗を誰も拾えなかった。
実際 `camera_unit_lid` は長辺 198 mm を四隅 4 点で押さえており、
人間の指摘で調べたら**中央の圧縮率が 25% -> 13.3% に落ちていた**（下限 15% 割れ）。
**水が入るまで外から見えない失敗**なので、屋外筐体では致命的である。

**手法**: 設計が `SEAL_SPANS` を宣言すると、

1. **`build()` した形状**を 0.4 mm の板でスライスし、体積特性から
   断面二次モーメント I(z) を**実測する**（設計側に数字を書かせない）
2. 蓋を Hermite 梁要素の梁、パッキンを**非線形の弾性床**として Newton 法で解く
3. 合わせ面に沿った**潰し量の最小値**を出す

```python
def SEAL_SPANS(p=PARAMS):          # 定数でも、params を取る関数でもよい
    return [seal.SealSpan(
        name="lid_long_edges", z0=3.0, z1=195.0,
        supports=(12.0, 142.0, 186.0),          # 締結点の z
        gasket=seal.Gasket(cord_mm=2.0, groove_depth_mm=1.5,
                           shore_a=70.0, lines=2),
        end_run_mm=78.0,           # 短辺のパッキン長さ（両端の集中荷重になる）
    )]
```

**パッキンの反発力の出し方**（`harness/seal.py`）:

```
E [MPa] = 0.0981 (56 + 7.62336 S) / (0.137505 (254 - 2.54 S))      Gent（硬度 -> 弾性率）
w(eps)  = E d (1.25 eps^1.5 + 50 eps^6)   [N/mm]                   Lindley（O リングの圧縮）
```

**判定**（静的フェイスシールの圧縮率）:

| 圧縮率 | 判定 | 意味 |
|---|---|---|
| 15% 未満 | **FAIL** | 面の粗さを埋めきれず漏れる |
| 15 〜 20% | WARN | 成立はするがクリープと反りの余地が無い |
| 20 〜 35% | PASS | 静的シールの常用域 |
| 35% 超 | WARN | 圧縮永久ひずみ。次に開けたとき戻らない |

閾値は `seal_min_squeeze_frac` / `seal_target_squeeze_frac` /
`seal_max_squeeze_frac` で設計ごとに上書きできる（外すなら理由を docstring に）。

**モデル自体の検証**: `tests/test_seal_model.py` が閉じた式と突き合わせている
（等分布荷重の単純支持梁 = `5wL^4/384EI` と 1% 以内、支間半減で 1/16 x 0.415）。
**モデルが間違っていれば判定も全部間違っている**ので、ここは必ず維持すること。

**限界**:
- **反りと平面度を見ていない。** 198 mm の ASA の反りは、ここで計算する
  弾性変形（0.08 mm）より大きくなりうる。**実機で定盤に当てて測ること**
- **クリープと圧縮永久ひずみを見ていない。** 出るのは「締めた直後」の値
- 梁は Euler-Bernoulli。せん断たわみと shear lag（幅に対しスパンが短いと効く）は
  実効弾性率の係数 `PRINT_KNOCKDOWN`（既定 0.6・**推定**）でまとめて割り引いている
- 疎充填で刷ると実体より柔らかい。これも同じ係数に含めている（実測していない）
- 相手側（本体のリム）は剛体としている
- O リングの反発力は一般式であって、**その品番の実測ではない**
- 締結点では蓋が land に密着していると仮定している。ねじが緩む側の失敗は見ない
- 梁は 1 方向にしか曲げない。短辺側（幅方向）のたわみは別途考えること

## 11. captive — 捕捉式ねじが「落ちない・抜けきる・平らに座る」か

**なぜ要るのか**: 現地で保守するのは機械に強くない人で、屋久島の林床で落とした
ねじは落ち葉の中で二度と見つからない（`docs/AGENTS.md` §4.9 原則 1）。
だから蓋を外したとき**蝶ねじ 6 本は蓋に付いたまま残らなければならない。**

それは「リテーナ（止め輪 / 押しナット）を軸に付け、蓋の内側のポケットで受け止める」
という**寸法の連鎖**で成立する。連鎖が切れると次のどれかになる。

| 切れ方 | 現地で何が起きるか |
|---|---|
| リテーナを受ける肉が無い | **ねじが抜けて落ちる**（二度と見つからない） |
| ポケットが浅い | 抜けきる前にリテーナが止まって **蓋が開かない** |
| ねじが短い | 相手に届かない |
| ねじが長い | **下穴の底を突いて**、締めたつもりで面圧が出ない |
| ポケットが深すぎ / ねじが短すぎ | 緩めきってもねじ先が出たままで**蓋を平らに置けない** |

**どれも `wall` / `openings` / `layout` / `seal` は一切見ていない。**
しかも現地に行くまで気づけない。だから専用のチェックにした。

### 何をしているか

設計が `CAPTIVE_SCREWS`（`harness.captive.CaptiveScrew` のリスト、または params を
取る関数）を宣言すると、**`build()` した形状にねじ軸と平行なレイを飛ばして**

  - リテーナ probe（半径 `retainer_od/2 - 0.2`）… 最初に当たる肉まで = **ポケットの深さ**
  - 頭 probe（半径 `head_dia/2 - 0.2`）… 最後に肉が切れるところ = **頭の座面の深さ**

を実測し、`travel = ポケット - リテーナの厚み` から成立条件を解く。
**PARAMS の値ではなく形から測る**ので、形を触れば数字が動く。
周方向に 4 本飛ばし、ばらつきが 0.2 mm を超えたら「円対称でない」と警告する。

### 閾値

| 条件 | 判定 |
|---|---|
| リテーナ径の位置に肉が無い / `travel <= 0` | **FAIL**（捕捉されない） |
| `engage <= 0` | **FAIL**（届かない） |
| `engage > insert_depth` | **FAIL**（下穴の底を突く） |
| `travel < engage + release_margin`（既定 1.0） | **FAIL**（蓋が開かない） |
| `protrude >= gap` | **FAIL**（平らに置けない） |
| `engage < 呼び径 x 1` | WARN（噛み合いが浅い） |

### 限界（何を見逃すか）

- **リテーナの保持力**。押しナットや止め輪が何 N で抜けるかは入れていない。
  **ここで見ているのは寸法の連鎖だけである**
- **リテーナがねじ山の上を歩いて位置がずれる**失敗（ゴムの O リングや
  ねじ込みナットで起きる）。止め輪・押しナットは軸方向の止めなので歩かないが、
  それは**形式の選択**であって、ここで検証してはいない
- **リテーナの厚みは申告値**（実測ではない）。厚いリテーナは逃げをそのぶん食う
- ねじの実長のばらつき、インサートの座面が沈む / 飛び出す量、蓋の反り。
  **噛み合いが数 mm しか無い設計ではこの積み上げ公差が効く**
- リテーナがポケットに実際に**入る**か（径はカタログの推定値）
- **面圧への影響**。ポケットを彫れば蓋の断面は痩せる。それは `seal` の仕事なので、
  捕捉機構を触ったら **`seal` を必ず併せて回すこと**

## レンダについて

`out/<design>/views/` に 6 面 + iso + 断面。断面は「手前半分を実際にブーリアンで
切り落としたソリッド」を法線方向から見ている。切り口がカメラ正面に来るので、
パッキン溝と肉厚がそのまま読める。

既定の断面は XZ 中央と YZ 中央。設計側で `SECTIONS` を定義すれば任意の面で切れる。

バックエンドは VTK（EGL オフスクリーン）。失敗したら numpy の Z バッファによる
ソフトウェアラスタライザに自動で落ちる。`ENCL_RENDERER=soft` で強制もできる。
どちらを使ったかは `report.md` の先頭に出る。

## チェックを足すとき

1. `harness/checks/<name>.py` を作り、`@register("<name>")` を付ける
2. `CheckResult(name, status, summary, measurements, table=..., limits=...)` を返す。
   **`measurements` に実測値を必ず入れる。PASS/FAIL だけ返すチェックは受け付けない。**
   **`limits` に「何を見逃すか」を必ず書く。**
3. `harness/checks/__init__.py` の `ORDER` に並べる
4. `tests/test_checks_negative.py` に「壊した設計で FAIL する」テストを足す

**ネガティブテストが無いチェックは未完成とみなす。**
