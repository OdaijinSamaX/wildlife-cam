## 1. 減衰の「合格」を時定数 τ で測る（監査 順位1）

### 何を

- 閾値を跨いだ**時刻**ではなく、下り坂で **2.0V を切った時刻と 1.0V を切った時刻の差 `t_half`**
  を測るようにした。`t_half = τ・ln2` なので**ピーク電圧に依存しない**。
- 合格帯は**固定値にしない**。`config.h` の `DECAY_TAU_BASELINE_MS`（据付時に一度測った値）
  の **±40%**。初期値は **0 = 未設定**で、そのあいだは **ok とも urgent とも言わず `unknown`** を出す。
- 従来の「1300mV を割るまでの ms」も**そのまま印字を残した**（過去ログと比較できるように）。
- ハング時（core0 sampler 側）でも同じ `t_half` を出すようにした。

### なぜ

設計書 §5.2 の「1.3V を割るまで約1.5秒」が10倍の書き間違いで、健康な回路の実測は 67〜76ms。
合格窓 0.8〜3.0秒には**健康な回路が入らず、R_pd が外れた故障（約1.7秒）のほうが入る**。
毎晩 urgent が飛び、4日目には読まれなくなり、最後は検出器が手で無効化される。

### どう検証するか

焼いて `p`（強制ON 3秒）を押し、切れた直後の行を見る。**据付直後はこう出るのが正常**:

```
[減衰] 計測開始 V_pump=2790mV
[減衰] V_pump<1300mV まで 70 ms
[減衰tau] 通常OFF t_half=66 ms (2000→1000 mV) peak=2790 mV 判定=unknown(基準未設定)
          → 据付時の値です。config.h の DECAY_TAU_BASELINE_MS に 66 を書き写して焼き直してください。
```

- **`t_half` が 40〜90ms 付近** → 健康。その数字を `config.h` に書き写して焼き直す。
- **`t_half` が 1000ms 超** → R_pd かゲートの脚が外れている。**配線を見る**（焼き直しではない）。
- 書き写して焼き直したあとは、毎回こう出る:

```
[減衰tau] 通常OFF t_half=64 ms 判定=ok (基準 66 ms ±40% = 39〜92 ms) peak=2790 mV
```

- 故障したときはこう出る（13日間これを grep すればよい）:

```
[減衰tau] 通常OFF t_half=1386 ms 判定=NG(遅い: R_pd かゲート脚が外れた疑い) (基準 66 ms ±40% = 39〜92 ms) peak=2790 mV
```

- 測れなかったときも**必ず言う**（黙って走らないことが無いようにする）:

```
[減衰tau] 通常OFF t_half=unknown (3000 ms 以内に 1000 mV まで落ちず) peak=2790 mV
[減衰] 計測せず: ピークが 1800 mV で下限 2000 mV に届かず (通算 3 回)
```

**タイミング余裕**（実機が無いので机上で確認した）: R_pd が外れた最悪ケース（τ≈2s）でも、
ピーク 2.79V から 1.0V まで **約 2052ms**、無負荷 3.13V からでも **約 2282ms** で、
`DECAY_TIMEOUT_MS`(3000ms) の内側に収まる。だから故障側も `unknown` に落ちずに
ちゃんと `NG(遅い)` として出る。`DECAY_TIMEOUT_MS` は変えていない。

## 2. T_cap 45秒を「ランプの実態」に付け替えた（監査 順位2 — 唯一の安全側）

### 何を

- `lamp_hot_since_us` を新設。**PUMP 出力が連続 500ms 低かったときだけ**クリアする
  （`config.h` の `LAMP_COOL_US`）。45秒はこれを起点に数える。
- デューティ計上も同じ変数を基準にし、**10秒 × 60個のリング（120バイト）でずらして数える**。
  窓の一括ゼロクリアは廃止。上限 5分/600秒、解除は 4分30秒（ヒステリシス）。
- **ベンチ強制ON（`p`）にも同じ 45秒を効かせた。**
  45秒は「どの経路が点けたか」に依らずランプの実態に対する絶対上限であるべきなのと、
  **Pi 側に ON/OFF を撃つ道具が無い**ため（`ble_advertiser.py` に `--want` 相当が無い）、
  実機でこの直しを確かめられる唯一の道がこれだから。`p` は既定3秒なので通常運用には影響しない。

### なぜ

BLE の広告間隔は 100ms 固定、ランプが消えるには 150ms かかる。
**OFF → 100ms 後に ON を繰り返すと、ランプは一度も消えないのに 45秒の時計だけがゼロに戻り続ける。**
デューティ上限も、①ON 指令の時間しか数えない ②10分窓を丸ごとゼロクリアする、の二重で効かない。
結果、ランプが最長10分連続で点き、一晩分の IR 電池 83mAh を10分で使い切る。
さらに点滅中は MOSFET が線形領域を通過し、放熱器なし TO-220・密閉箱・周囲45℃で
監査 §15.2 R2 の「層1〜5 のどれでも防げない唯一の故障」を自分で作りかねない。

### どう検証するか

**2-A. 母艦で実施済み（実機不要・結果を下に貼る）**

`.ino` の `process_frame` / `service_state` / `lamp_track` を**そのまま呼ぶ**試験台を書いて、
監査が書いている交互点滅（OFF と ON を 100ms 交互）を 120 秒ぶん流した。

| | 旧版 (`.bak`) | 新版（今回） |
|---|---|---|
| ランプ実点灯の最大連続 | **119,899 ms**（試験全域。一度も切れない） | **45,399 ms**（45秒＋冷却待ち 0.4秒） |
| T_cap 到達 | **0回**（S5_LIT のまま） | **1回** → COOLDOWN へ |
| 実点灯の合計 / 120秒 | 60,000 ms | 29,900 ms |

正常な30秒イベントでは T_cap は**0回**、デューティ計上は約 30,500ms で、誤爆しないことも確認した。

**2-B. 実機で（ベンチだけで確認できる。Pi 不要）**

`p` を **2秒ごとに押し続ける**（`p` は3秒ぶんなので、押し続けるかぎりランプは消えない）。
45秒経つとこの行が出て、強制ONが打ち切られる:

```
[BENCH] 強制ON を T_cap 45秒(ランプ実点灯基準)で打ち切りました
[lamp] PUMP が連続 500ms Low → ランプは冷えたと判定(実点灯 45000 ms で終了)
```

押すのをやめて 0.5秒経つと `lamp_hot` は 0 に戻る（`s` で確認できる）。
**旧版では、何秒押し続けても打ち切られない。** そこが直った点。

**2-C. 13日間のログで見るところ**

10秒ごとの beaconB に、この1行が出るようにした。**これだけ grep すれば足りる**:

```
[beaconB] lamp_hot=0ms duty600=0/300000ms tcap_hit=0 duty_limit=0 tau{last=66ms,ok=41,ng=0,unknown=1} decay_skip=0
```

- `tcap_hit` が増えていたら、45秒上限が実際に働いた＝異常な点灯要求が来ている。
- `duty600` が 300000 に張り付き `(制限中)` が付いたら、点けすぎで抑えられている。
- `lamp_hot` が 45000 を超えることは**構造上ありえない**。超えていたらこの直しが効いていない。

正常イベントのときは:

```
[T_cap] ランプ実点灯が 45000 ms 連続 → 45秒上限で強制消灯(通算 1 回)
[deadman] PUMP OFF (T_cap 45秒到達(ランプ実点灯基準))
[duty] 直近600秒の実点灯 300000 ms が上限 300000 ms に到達 → 制限(通算 1 回)
[duty] 直近600秒の実点灯が 269000 ms まで低下 → 制限解除
```

## 3. シャントの「独立確認」（監査 順位3）

**→ この1行の削除は人間の作業として下の「やることリスト」に出した。**

### 代わりにファームでやったこと（穴を作り直させないため）

`config.h` の `PIN_SHUNT` の直下に、消してはいけない理由をコメントで固定した:

## 4. HMAC 鍵を「人間が貼るだけの空欄」にした（監査 順位2(b)）

### 何を

**鍵の値は決めていないし、どこにも書いていない。** 用意したのは仕組みだけ:

- `config.h` の先頭に `#define HMAC_KEY_IS_PLACEHOLDER 1` を置いた。
  - **1（今の状態）**: 従来どおり公開テスト鍵で動く。ただし
    **コンパイル時に `#warning`**、**起動時に★枠の警告**、**beaconB の毎行に警告**が出る。
  - **0**: 【本番鍵の空欄】のバイト列を使う。空のまま 0 にすると
    `static_assert` で**ビルドが止まる**（＝鍵無しのファームは焼けない）。
- 貼り方と「Pi 側と同時に替える」手順を `config.h` のコメントに書いた。
- **鍵の値はシリアルに一切出さない。** 長さも出さない。

母艦で両方の分岐を確認済み:

| 状態 | 結果 |
|---|---|
| `PLACEHOLDER 1`（今） | ビルド通る＋`#warning` が出る |
| `PLACEHOLDER 0` で空欄のまま | **ビルド失敗**: `HMAC_KEY が空か短すぎます: config.h の【本番鍵の空欄】に 16 バイト以上を貼ってください` |
| `PLACEHOLDER 0` で32バイト貼付 | ビルド通る・警告なし |

### なぜ

無人13日を走らせる前提で、この穴の発火条件のひとつが「鍵を持っている誰か」だから。
公開テスト鍵は Pi 側スクリプトの既定値として世に出ている。

### どう検証するか

**貼る前**（今の状態。この画面が出たら**まだ焼いてはいけない**）:

```
★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★
★ 警告: HMAC 鍵が config.h の公開テスト鍵のままです。
★ 無人運用(8/26〜9/8)に投入してはいけません。
★ config.h の【本番鍵の空欄】に鍵を貼り、HMAC_KEY_IS_PLACEHOLDER を 0 に。
★ ※Pi 側 ble_advertiser.py の --key と必ず同時に替えること。
★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★★
```

**貼ったあと**（この1行になっていること。★枠が消えていること）:

```
[鍵] HMAC は本番鍵で動作します(値は表示しません)。Pi 側と一致していることを確認してください。
```

**鍵が Pi と食い違っていないこと**は、これで判定する:
